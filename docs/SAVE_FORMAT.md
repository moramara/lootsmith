# セーブデータと設定ファイルの形式

セーブ/設定ファイルの形式、バージョン履歴、互換性ポリシーの正本です。レコードごとの正確なフィールド一覧は実装と同じ場所にあり、
**`src/core/save.c` の冒頭のコメント**が正本です (重複を避けるため、ここには転記しません)。

## セーブファイル (`lootsmith.sav`)

- プレーンテキストで、1 行に 1 つの `key values...` レコード。先頭行は `LOOTSMITH_SAVE <version>`、末尾は `end`。
- 現在の `SAVE_VERSION` は **4** です (`src/core/simulation.h`)。`SAVE_MIN_VERSION` が、今も読める最も古い形式です。
- 場所は作業ディレクトリ (`--save FILE` で変更)。新しい日の始まりごとに自動保存されます。
- 書き込みは原子的です。`<path>.tmp` に書いてフラッシュ・同期した後に置き換えるので、途中で失敗しても元のセーブは残り、
  こちらが作った一時ファイルだけが削除されます (`SAVE_ERR_IO`)。

## バージョン履歴

| バージョン | 追加されたもの |
|---|---|
| 1 | 最初の形式 |
| 2 | ギルド: `greport`、`guild`、`gboard` + `gb` 行、`gactive` + `ga` 行。v2 以上ではすべて必須で、件数がレコードと一致していること |
| 3 | 装備の品質と特性: すべての `item` 行の末尾 2 フィールド `<quality> <trait>` と、`craft <u32>` (クラフトの乱数状態)。v3 ではどちらも必須 |
| 4 | 契約の種類と報酬素材: すべての `gb` / `ga` 行の末尾 3 フィールド `<kind> <reward_mat> <reward_qty>` (Dragon Hunt の掲示中・受注中の状態)。v4 では 11 フィールドすべてが必須 |

`counts <mat> <eq> <cust> <up>` は、保存時に各コンテンツテーブルにいくつ ID が存在したかを表します。バージョンとは独立しており、
コンテンツの追加ではバージョンを上げません。

## 互換性ポリシー

- コンテンツ ID (素材、装備、客、アップグレード) は追記のみなので、古いビルドのセーブは、今も存在し意味も変わっていない ID だけを参照します。
- **新しく追加されたコンテンツ**: そのセーブには `mat` / `up` レコードがありません。破損とは扱わず、初期値 (在庫なし、基準価格、
  アップグレードのレベル 0) で埋めます。バージョンを上げる必要はありません。
- **`counts` が教えるレコードの欠落**: セーブが *知っていた* ID のレコードが欠けていれば、破損として報告します。`counts` 導入前の
  セーブは、最初のリリースの内容 (`LEGACY_COUNTS`) を持つものとして扱います。
- **より新しいゲームのセーブ**: このビルドより多くのコンテンツを知っている (`counts` が大きい) セーブは `SAVE_ERR_VERSION` で拒否され、
  何も読み込まれません。
- **`SAVE_VERSION` を上げるとき**: 既存のレコードの意味が変わったとき、ID を削除・並べ替えたとき、または既定値で済ませられない状態を
  追加したときだけです。上げたら、古いレイアウトの読み込みを残し、`game_load()` の「version fix-ups」ブロック (解析の後、検証の前に実行される)
  で変換します。
- 未知のキーは無視されます (前方互換性)。

## 古い形式の移行

- **バージョン 1 (ギルドなし)**: `guild_migrate_legacy()` が、保存された `rng` と日付から (それを消費せずに) `guild_rng` を導出し、
  受注中の契約をなしにし、累計を 0 にし、現在の日付用の掲示板を新しく生成します。それ以外は引き継ぎます。v1 のファイルにあるギルドのキーは
  未知のキーとして無視されます。
- **バージョン 1 と 2 (品質なし)**: すべてのアイテムは Common / 特性なしになり、保存された能力値・原価・価値・推奨価格・価格は **そのまま**
  引き継がれます (何も再計算しない)。`craft_migrate_legacy()` が、保存された `rng`、`guild_rng`、日付から、どの乱数ストリームも
  消費せずに `craft_rng` を導出します。v2 のファイルにある `craft` 行は未知のキーとして使われません。
- **バージョン 1〜3 (契約の種類なし)**: `gb` / `ga` は 8 フィールドで、すべて通常契約 (`kind = 0`、報酬素材なし) として復元します。
  Dragon Scale の報酬が旧契約に付くことはありません (Wyrm Hunter の契約でも同じ)。再保存すると v4 の形式になります。
- 素材 Dragon Scale (素材 ID 7) の追加はコンテンツの追加なので、`counts` が素材 7 つのセーブには `mat 7` がなく、在庫 0・基準価格で
  読み込みます (バージョンとは独立)。
- v3 では、1 つしかないはずのキー (`craft` など) の重複も拒否します。古い形式でも、`mat` / `up` レコードの重複は拒否されます
  (後勝ちの上書きはしません)。

## 検証

読み込んだ状態は `game_validate()` を通り、すべて問題ない場合にだけ呼び出し側へコピーされます。失敗した場合、読み込み先の
`GameState` には一切触れません。主な規則:

- ID が有効で、アイテム・客・契約は書き手が知っていた ID だけを使う (契約の報酬素材も同じ)
- 契約の種類と報酬が整合している: 通常契約は報酬なし (素材 0・数 0)。Dragon Hunt は、市場で買えない (`hunt_only`) 素材 1 つを数 1..99 で持ち、
  依頼主は Wyrm Hunter で、`guild_done` が 50 以上のときにだけ存在できる。掲示板の Dragon Hunt は最大 1 件
- Common / Fine は特性を持たず、Masterwork / Legendary は特性をちょうど 1 つ持つ。`craft_rng` は 0 でない
- ギルドの記録がすべて存在し、件数が一致する。契約の ID は両方の配列をまたいで一意で、掲示板の契約の期限は 0、受注中の契約は実際の期限を持つ
- 解放されていない装備や客 (在庫、待ち行列、契約) は、その `guild_done` では存在できない。ランクと解放は `guild_done` から導出するため、
  保存はされない
- 状態と失敗理由が整合している (`ST_FAILED` ⇔ 本物の失敗理由)。累計・1 日分のレポート・所持金は上限の範囲内 (下記)

### 数値の解析と上限

- 数値は `strtoll` で読みます (10 進のみ、1 桁以上、`ERANGE` と範囲を検査、トークンは空白で終わること)。数値でない、または収まらない値は
  `SAVE_ERR_FORMAT`、許可された範囲を外れた有効な数値は `SAVE_ERR_VALUE` です。
- 到達可能なあらゆる状態を保存でき、かつ読み込めるように、上限は `simulation.h` に集約され、`game_validate()` が同じ数値で検証します。
  実際の定数と、飽和演算などの実装上の扱いは [DEVELOPMENT.md](DEVELOPMENT.md) の「数値の上限」を参照してください。

## 設定ファイル (`lootsmith.cfg`)

セーブとは別のファイルで、形式もセーブには影響しません。場所は作業ディレクトリ (`--settings FILE` で変更) です。

```
LOOTSMITH_SETTINGS 1
bgm_volume 35
se_volume 65
```

- 音量は 0〜100 の整数パーセント。ファイルがない場合も、壊れている場合も、必ず有効な値が得られます (ファイルがなければ既定値、
  壊れたキーはそのキーの既定値、範囲外の数値は丸め、未知のキーは無視、ヘッダが違えばすべて既定値)。読み込みは 1 KB までです。
- 書き込みは `<path>.tmp` を経由した置き換えで、失敗してもメッセージを出すだけで致命的ではありません。
- 書き込むタイミングは、スライダーのドラッグを離したとき、キーボード操作が止まって 0.6 秒たったとき、OPTIONS を離れたとき、終了時です。
  ドラッグ中の毎フレームには書きません。実装は `src/audio/settings.c` です。
